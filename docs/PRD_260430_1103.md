- 문서 버전: v1.0
- 문서 목적: 브라우저 기반 음원 조정 프로그램의 MVP 범위, 기능 요구사항, UX 원칙, 기술 방향, 구현 우선순위를 정의한다.

---

## 1. 프로젝트 개요

### 1.1 프로젝트명(가칭)
**Audio Adjuster**

### 1.2 제품 개요
개인 사용자를 위한 **브라우저 기반 음원 조정 프로그램**을 개발한다. 사용자는 mp3 파일을 업로드한 뒤, 브라우저 UI에서 음원을 자르거나, key/bpm을 분석하거나, key를 반음 단위로 변환하거나, 음량을 증폭하거나, 4채널로 분리한 뒤 믹스를 조정하여 결과물을 다운로드할 수 있어야 한다.

이 프로그램은 **브라우저 UI + 로컬 백엔드** 구조로 동작하며, 업로드 파일과 처리 결과물은 **세션 종료 후 별도로 저장하지 않는다.** 임시 파일은 로컬에서만 처리하며, 서버/클라우드 업로드를 전제로 하지 않는다.

### 1.3 개발 원칙
- **개인 사용**을 전제로 한다.
- **브라우저에서 조작 가능**해야 한다.
- **모든 데이터 처리는 로컬 중심**으로 수행한다.
- **세션 종료 후 히스토리/음원 영구 저장 없음**을 기본 정책으로 한다.
- 기능은 **1페이지부터 순차적으로 구현 및 테스트**한다.
- 각 페이지는 구현 전 반드시 **해당 페이지의 기능이 모두 표현된 디자인 시안**을 먼저 확정한다.

## 2. 목표와 비목표

### 2.1 목표
1. mp3 파일을 업로드하여 브라우저에서 바로 편집/분석/변환할 수 있는 환경 제공
2. 초보자도 이해하기 쉬운 직관적 UI 제공
3. 실사용에 필요한 핵심 기능만 담은 개인용 MVP 완성
4. 페이지별로 점진적으로 완성도를 높이며 안정적으로 테스트 가능한 구조 확보
5. 로컬 백엔드 기반으로 무거운 처리(분석, 분리, 변환)를 안정적으로 수행

### 2.2 비목표
1. 회원가입/로그인/계정 시스템
2. 멀티유저 협업 기능
3. 서버 업로드 기반 중앙 저장소
4. 세션 종료 후 작업 이력 자동 복구
5. 모바일 우선 지원
6. mp3 외 포맷(m4a, wav, flac 등) 지원
7. DAW 수준의 전문 편집 기능 전체 제공

## 3. 대상 사용자

### 3.1 1차 대상 사용자
- 본인 1인 사용
- Windows 데스크톱 환경에서 Chrome 브라우저를 사용하는 사용자
- 음악 편집 전문가가 아니어도 쉽게 사용할 수 있어야 함

### 3.2 핵심 사용 시나리오
- 원하는 구간만 잘라서 mp3로 저장하고 싶다.
- 현재 곡의 대략적인 key와 bpm을 빠르게 확인하고 싶다.
- 반음 단위로 key를 바꾸되, 템포는 유지하고 싶다.
- 음량을 키우거나 줄이면서 실시간으로 들어보고 싶다.
- 보컬/드럼/베이스/기타로 대략 분리한 뒤 특정 파트를 키우거나 줄여서 mix 결과를 저장하고 싶다.

## 4. 제품 범위(MVP)

본 MVP는 아래 **5개 페이지**로 구성한다.

1. **음원 자르기**
2. **음원 분석**
3. **Key 변환**
4. **음량 증폭**
5. **세션별 분리 및 음량 조절**

각 페이지는 독립적으로 동작하되, 공통 업로드/재생/UI 패턴은 일관성을 유지한다.

## 5. 공통 정책

### 5.1 지원 환경
- OS: Windows 우선
- 브라우저: Chrome 데스크톱 우선
- 네트워크: 인터넷 연결이 필수는 아니며, 로컬 실행 우선

### 5.2 지원 파일
- 입력: **mp3만 지원**
- 출력: **mp3만 지원**

### 5.3 업로드 제한
- 1회 업로드 1곡 기준
- 최대 길이: **10분 이하**
- 최대 용량: **20MB 이하**

### 5.4 저장 정책
- 임시 저장소는 로컬 사용
- 세션 중 생성되는 파일은 임시 저장 가능
- 세션 종료 후 히스토리/음원/설정은 별도로 보존하지 않음
- 자동 저장, 최근 파일 목록, 사용자 계정 연동 기능은 제공하지 않음

### 5.5 UX 공통 원칙
- 모든 페이지에서 업로드 상태, 처리 상태, 오류 상태를 명확히 안내
- 처리 시간이 길 수 있는 기능은 진행 상태를 표시
- 미리듣기와 다운로드는 명확히 분리
- 초보자도 이해할 수 있도록 전문 용어 최소화
- 주요 버튼은 일관된 위치와 라벨 사용

### 5.6 디자인 공통 원칙
각 페이지 구현 전 **디자인 시안부터 먼저 완성**한다.

디자인 시안에는 최소한 아래가 표현되어야 한다.
- 업로드 영역
- 파형/분석/컨트롤 배치
- 재생 및 정지 버튼
- 현재 선택값 표시 영역
- 처리 실행 버튼
- 결과 확인 영역
- 다운로드 버튼
- 오류/가이드 메시지 영역

## 7. 페이지별 상세 요구사항

# 7.1 1페이지: 음원 자르기

## 7.1.1 목적
사용자가 mp3의 원하는 구간만 선택하여 잘라낸 뒤 다운로드할 수 있도록 한다.

## 7.1.2 핵심 기능
- mp3 업로드
- 파형 표시
- 좌측 바(시작점) 조절
- 우측 바(종료점) 조절
- 선택 구간 길이 표시
- 원본 재생
- 구간 기준 미리듣기
- 자르기 실행
- 결과 다운로드

## 7.1.3 UI 구성
- 업로드 영역
- 파형 뷰어
- 좌측/우측 선택 바
- 현재 시작 시점 / 종료 시점 / 총 선택 길이 표시
- 재생/정지 버튼
- 자르기 실행 버튼
- 다운로드 버튼

## 7.1.4 동작 규칙
### 시작 바(좌측 바)
- 사용자가 시작 바를 이동하여 자를 시작 지점을 지정한다.
- 재생 버튼을 누르면 **해당 바 위치부터 끝까지 계속 재생**한다.

### 종료 바(우측 바)
- 사용자가 종료 바를 이동하여 자를 끝 지점을 지정한다.
- 우측 바 미리듣기 시에는 **해당 지점 5초 전부터 재생**한다.
- 5초 전 구간이 음원 시작점보다 앞서면 가능한 시작 지점부터 재생한다.

### 구간 자르기
- 최종 잘라낼 구간은 `시작 바 ~ 종료 바` 구간이다.
- 시작점이 종료점 이상이면 실행 불가 처리
- 잘라낸 결과는 별도의 결과 오디오로 생성

## 7.1.5 다운로드 파일명 규칙
- `원본음원명+(cut).mp3`

예시:
- `song+(cut).mp3`

## 7.1.6 예외 처리
- 파일 미업로드 상태에서는 실행 버튼 비활성화
- 시작점 >= 종료점이면 오류 메시지 표시
- 길이 0초 또는 매우 짧은 구간이면 경고 표시

## 7.1.7 수용 기준
- 사용자가 시각적으로 구간을 선택할 수 있어야 한다.
- 시작/종료 기준 미리듣기가 의도대로 동작해야 한다.
- 선택 구간이 정확히 잘린 mp3 다운로드가 가능해야 한다.

---

# 7.2 2페이지: 음원 분석

## 7.2.1 목적
업로드한 mp3의 **대략적인 key와 bpm**을 사용자에게 참고용으로 제공한다.

## 7.2.2 핵심 기능
- mp3 업로드
- 분석 실행
- key 추정값 표시
- bpm 추정값 표시
- 전체 재생

## 7.2.3 UI 구성
- 업로드 영역
- 전체 재생 버튼
- 분석 버튼
- 결과 카드
  - Key
  - BPM
  - 참고용 안내 문구

## 7.2.4 분석 정책
- 결과는 **대략적 참고용**이다.
- 절대 정확한 음악 이론 판정 도구가 아님을 UI에 명시한다.
- 분석 실패 또는 신뢰도 부족 시 `Unknown` 또는 이에 준하는 상태 표기 가능

## 7.2.5 Key 표시 방식(권장)
UI 표기는 아래 형식을 사용한다.
- `C Major`
- `A minor`
- `F# minor`
- `Bb Major`

## 7.2.6 안내 문구
예시:
- `분석 결과는 참고용 추정값이며 실제 조성과 다를 수 있습니다.`

## 7.2.7 수용 기준
- 업로드 후 전체 재생 가능
- key 및 bpm 추정 결과가 UI에 표시됨
- 실패 시 사용자에게 이해 가능한 메시지를 보여줌

# 7.3 3페이지: Key 변환

## 7.3.1 목적
업로드한 음원의 key를 **반음 단위로 상/하향 변환**하고, 변환 결과를 mp3로 저장할 수 있도록 한다.

## 7.3.2 핵심 기능
- mp3 업로드
- 원본 key, bpm 표시
- 원본 전체 재생
- 반음 단위 key up/down 조절
- 템포 유지한 상태로 변환
- 변환 결과 전체 재생
- 변환 결과 다운로드

## 7.3.3 변환 범위
- **±12 semitone**
- 0 semitone(변환 없음)도 허용

## 7.3.4 UI 구성
- 업로드 영역
- 원본 정보 카드
  - 추정 Key
  - 추정 BPM
- 원본 재생 버튼
- semitone 조절 UI
  - -12 ~ +12
- 변환 후 예상 key 표시
- 변환 실행 버튼
- 결과 재생 버튼
- 다운로드 버튼

## 7.3.5 동작 규칙
- 템포는 유지한다.
- 변환 전 원본 key/bpm을 표시한다.
- 사용자가 semitone 값을 변경하면 예상 key를 UI에 반영한다.
- 변환된 결과는 전체 재생 가능해야 한다.

## 7.3.6 파일명 규칙
파일명에는 **변환된 key 결과값**을 반영한다.

### UI 표기 권장안
- `G Major`
- `A minor`
- `F# minor`
- `Bb Major`

### 파일명 표기 권장안
파일명 안전성과 일관성을 위해 아래 규칙을 사용한다.
- 공백 → `_`
- `#` → `_sharp`
- `b`(flat) → `_flat`
- 장조/단조 표기 → `Major`, `minor`

예시:
- `song+(G_Major).mp3`
- `song+(A_minor).mp3`
- `song+(F_sharp_minor).mp3`
- `song+(B_flat_Major).mp3`

## 7.3.7 예외 처리
- 분석 key가 `Unknown`이어도 semitone 변환 자체는 허용 가능
- 다만 파일명은 실제 변환 target key를 계산 가능한 경우에만 key 기반으로 생성
- 계산 불가 시 fallback 파일명 정책 필요
  - 예: `원본음원명+(key_shift_+3).mp3`

## 7.3.8 수용 기준
- semitone 조절이 정확히 반영되어야 한다.
- 템포가 유지되어야 한다.
- 변환 후 전체 재생과 mp3 다운로드가 가능해야 한다.
- 파일명 규칙이 일관되게 적용되어야 한다.

# 7.4 4페이지: 음량 증폭

## 7.4.1 목적
사용자가 음원의 파형을 확인하면서 gain을 조절하고, 실시간으로 결과를 듣고, 최종 mp3를 다운로드할 수 있도록 한다.

## 7.4.2 핵심 기능
- mp3 업로드
- 파형 표시
- gain 조절
- 전체 재생
- 증폭 결과 미리듣기
- clipping 방지 옵션
- 결과 다운로드

## 7.4.3 UI 구성
- 업로드 영역
- 파형 뷰어
- gain 슬라이더 또는 숫자 입력
- clipping 방지 옵션 토글
- 현재 적용 gain 표시
- 전체 재생 버튼
- 적용/렌더링 버튼
- 다운로드 버튼

## 7.4.4 동작 규칙
- 사용자는 gain 값을 증감할 수 있다.
- 재생 중에도 조절값을 변경하며 결과를 확인할 수 있도록 설계한다.
- clipping 방지 옵션이 켜진 경우, 출력이 과도하게 찢어지지 않도록 후처리를 적용한다.

## 7.4.5 다운로드 파일명 규칙
- `원본음원명+(amp).mp3`

예시:
- `song+(amp).mp3`

## 7.4.6 수용 기준
- gain 조절 후 결과 차이를 청감상 확인할 수 있어야 한다.
- clipping 방지 옵션 on/off가 동작해야 한다.
- 결과 mp3 다운로드가 가능해야 한다.

---

# 7.5 5페이지: 세션별 분리 및 음량 조절

## 7.5.1 목적
업로드한 mp3를 4개 stem으로 분리하고, 각 stem의 볼륨을 조절하면서 mix 결과를 들어보고 다운로드할 수 있도록 한다.

## 7.5.2 분리 대상 채널
- 드럼
- 베이스
- 보컬
- 그 외(Other)

## 7.5.3 핵심 기능
- mp3 업로드
- 4채널 분리 실행
- stem별 개별 재생
- stem별 볼륨 조절
- 전체 mix 재생
- 개별 stem 다운로드
- mixed 결과 다운로드

## 7.5.4 UI 구성
- 업로드 영역
- 분리 실행 버튼
- 분리 진행 상태 표시
- 4개 stem 카드 또는 채널 패널
  - stem 이름
  - stem 재생 버튼
  - stem 볼륨 슬라이더
- 전체 mix 재생 버튼
- stem 다운로드 버튼들
- mixed 다운로드 버튼

## 7.5.5 동작 규칙
- 분리 처리 완료 후 4개 stem을 각각 제어할 수 있어야 한다.
- 각 stem의 볼륨 값 변경 시 mix 결과에 반영되어야 한다.
- 사용자는 전체 mix를 전체 재생으로 확인할 수 있어야 한다.
- 개별 stem과 mixed 결과를 모두 다운로드할 수 있어야 한다.

## 7.5.6 다운로드 파일명 규칙
### 개별 stem
- `원본음원명+(drums).mp3`
- `원본음원명+(bass).mp3`
- `원본음원명+(vocals).mp3`
- `원본음원명+(other).mp3`

### mixed 결과
- `원본음원명+(mixed).mp3`

## 7.5.7 품질 정책
- stem 분리는 완벽 분리가 아닌 **실사용 참고 수준**으로 간주한다.
- 분리 품질은 원본 곡 특성에 따라 달라질 수 있음을 안내한다.

## 7.5.8 수용 기준
- 4개 stem이 생성되어야 한다.
- 각 stem 볼륨 조절이 가능해야 한다.
- mixed 결과 재생 및 다운로드가 가능해야 한다.
- 개별 stem 다운로드가 가능해야 한다.

---

## 8. 공통 파일명 정책

### 8.1 기본 원칙
- 원본 파일명 기반으로 결과 파일 생성
- 접미사는 괄호 형태로 부여
- 출력은 mp3 유지

### 8.2 예시
- 자르기: `song+(cut).mp3`
- key 변환: `song+(G_Major).mp3`
- 증폭: `song+(amp).mp3`
- stem mix: `song+(mixed).mp3`
- stem 개별: `song+(vocals).mp3`

### 8.3 파일명 정규화 권장
- 공백 → `_`
- 허용되지 않거나 불안정한 특수문자는 제거 또는 대체
- key 표기용 `#`/`b`는 문자열 치환 사용

## 9. 기술 방향(권장안)

> 본 섹션은 구현 상세 설계의 기초 방향이며, 실제 DTL 단계에서 구체화한다.

### 9.1 전체 구조
- **Frontend**: 브라우저 UI
- **Backend**: 로컬 실행 백엔드
- **Audio Processing**: 로컬 CPU/GPU 기반 처리
- **Temp Storage**: 로컬 임시 디렉터리

### 9.2 권장 아키텍처
- 프론트엔드: React 계열 SPA
- 백엔드: Python 기반 API 서버
- 처리 도구 예시:
  - mp3 디코딩/인코딩
  - waveform 추출
  - 구간 자르기
  - pitch shift / tempo preserve
  - key / bpm 분석
  - stem separation

### 9.3 기술 선정 원칙
- Windows 로컬 실행이 쉬울 것
- Chrome에서 안정적으로 사용할 수 있을 것
- 개인용 MVP에 과하지 않은 복잡도를 유지할 것
- 1페이지부터 차례대로 확장 가능한 구조일 것

### 9.4 처리 방식 원칙
- 무거운 작업은 백엔드에서 수행
- UI는 업로드/재생/상태 표시/컨트롤에 집중
- 임시 파일은 작업 단위로 생성 후 정리

## 10. 비기능 요구사항

### 10.1 성능
- 10분 이하 / 20MB 이하 mp3 기준으로 실사용 가능한 처리 시간 제공
- 자르기/증폭 등 비교적 가벼운 기능은 빠르게 반응해야 함
- stem 분리, key 변환, 분석은 진행 표시 필수

### 10.2 안정성
- 잘못된 파일 형식 업로드 시 명확한 오류 처리
- 처리 중 실패 시 앱 전체가 멈추지 않도록 페이지 단위 오류 격리
- 세션 내 임시 파일 정리 정책 필요

### 10.3 사용성
- 초보자도 바로 이해할 수 있는 버튼명/가이드 문구 사용
- 파형/슬라이더/결과 카드 중심의 직관적 UI 제공
- 페이지별 작업 흐름이 최대한 비슷해야 함

### 10.4 보안/프라이버시
- 외부 서버 업로드 없이 로컬에서만 처리
- 세션 종료 후 기록을 남기지 않는 방향 유지
- 개인 사용 전제의 단순한 보안 모델 적용

---

## 11. 오류 및 예외 처리 요구사항

### 11.1 공통 오류
- 지원하지 않는 파일 형식
- 용량 초과
- 길이 초과
- 오디오 디코딩 실패
- 처리 엔진 실패
- 결과 파일 생성 실패

### 11.2 공통 UI 메시지 원칙
- 왜 실패했는지 이해 가능한 문장 사용
- 재시도 가능 여부 안내
- 기술적 스택트레이스 그대로 노출 금지

예시:
- `mp3 파일만 업로드할 수 있습니다.`
- `파일 길이는 10분 이하여야 합니다.`
- `음원 분석에 실패했습니다. 다른 파일로 다시 시도해 주세요.`

## 12. 디자인 요구사항

각 페이지는 구현 시작 전에 아래를 충족하는 **디자인 시안**이 먼저 있어야 한다.

- 버튼/슬라이더/정보 카드의 우선순위가 명확할 것

### 12.2 디자인 산출물 최소 범위

- 주요 컴포넌트 배치
- 상태별 화면
  - 초기 상태
  - 파일 업로드 후 상태
  - 처리 중 상태
  - 처리 완료 상태
  - 오류 상태

### 12.3 UX 우선순위
1. 한눈에 이해되는 구조
2. 자주 쓰는 기능의 빠른 접근
3. 재생/정지/다운로드의 명확성

## 14. 테스트 전략

### 14.1 공통 테스트 항목
- mp3 업로드 성공/실패
- 10분 이하/초과 파일 검증
- 20MB 이하/초과 파일 검증
- 재생/정지 동작
- 다운로드 결과 생성 여부
- 오류 메시지 표시 여부

### 14.2 페이지별 핵심 테스트
#### 1페이지
- 시작/종료 바 이동 정확성
- 시작점 재생, 종료점 5초 전 미리듣기 동작
- 잘라낸 구간 정확성

#### 2페이지
- key/bpm 분석 결과 노출
- Unknown 처리
- 분석 실패 메시지

#### 3페이지
- semitone 범위 제한(-12~+12)
- 템포 유지 여부
- 파일명 key 반영 여부

#### 4페이지
- gain 조절 반영
- clipping 방지 옵션 on/off
- 결과 재생/다운로드

#### 5페이지
- 4개 stem 생성 여부
- stem별 볼륨 변경 반영
- 개별 stem 및 mixed 다운로드 여부

## 16. 리스크 및 고려사항

### 16.1 분석 정확도 한계
- key/bpm은 참고용 추정값이므로 곡에 따라 오차 가능

### 16.2 stem 분리 처리 비용
- 4채널 분리는 다른 기능보다 무겁고 느릴 수 있음
- 로컬 PC 성능에 따라 처리 시간이 크게 달라질 수 있음

### 16.3 mp3 재인코딩 품질
- 일부 기능은 재인코딩 과정에서 미세한 품질 변화가 발생할 수 있음

### 16.4 브라우저 오디오 UX 제약
- 재생 위치 동기화, 파형 표시, 실시간 반영은 브라우저와 백엔드의 역할 분리가 중요

## 19. 최종 결론

본 프로젝트는 **브라우저 기반 개인용 음원 조정 도구**이며, 로컬 백엔드를 활용해 무거운 음원 처리 기능을 안정적으로 수행하는 방향이 적절하다.

MVP는 아래 원칙으로 진행한다.
- mp3만 지원
- 10분 이하 / 20MB 이하
- 로컬 임시 처리
- 세션 종료 후 저장 없음
- 1페이지부터 순차 구현 및 테스트
- 각 페이지 구현 전에 디자인 시안 선행

이 방향은 기능 범위를 과도하게 넓히지 않으면서도, 실제 사용에 필요한 핵심 흐름을 빠르게 완성할 수 있는 현실적인 출발점이다.
